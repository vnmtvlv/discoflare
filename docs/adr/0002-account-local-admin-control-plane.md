# Keep deployment authority in one account-local Discoflare Admin

Discoflare has one account-local control-plane binary with two setup modes. Each Cloudflare account contains one small Worker named `discoflare-admin`. The Worker uses Cloudflare OAuth for operator identity and an encrypted stateless session cookie; it does not require Cloudflare Access or D1. Managed Setup uses a public PKCE OAuth client to create the Worker and stores its renewable OAuth credential as encrypted Worker secrets, then discoflare.com discards its own session. Private Setup uses temporary OAuth only to create or repair Admin; the operator then creates one Account Admin Token and submits it directly to that Worker origin.

After Managed Setup installs Admin, Admin immediately creates the first base Installation on `workers.dev` with D1, R2, KV, core Durable Objects, Workers AI, and an Owner Setup Claim. Agent Computer, RealtimeKit, custom domains, and email remain explicit later actions from Workspace Settings. Discoflare Admin also discovers every marked Installation in the account and owns creation, updates, repair, and those optional infrastructure operations. The broad credential never enters an Installation. Each workspace instead receives a service binding to Admin and a per-Installation capability derived from Admin's stable session secret and accepted only by fixed operation allowlists. Workspace chat and data continue without Admin; infrastructure changes and new Huddle API calls require it.

Cloudflare grants still use account and zone resource boundaries. A dedicated Cloudflare account therefore provides the strongest isolation; an existing paid account shares its authority boundary across the Installations that Admin manages. The source/CLI deployment path remains an operator escape hatch. Managed and Private differ only in whether Admin stores a renewable OAuth credential or an operator-supplied account token.
