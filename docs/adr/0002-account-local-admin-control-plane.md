# Keep deployment authority in one account-local Discoflare Admin

Discoflare has one account-local control-plane binary with one guided setup mode. Each Cloudflare account contains one small Worker named `discoflare-admin`. The Worker uses Cloudflare OAuth for operator identity and an encrypted stateless session cookie; it does not require Cloudflare Access or D1. Managed Setup uses a public PKCE OAuth client to create the Worker and stores its renewable OAuth credential as encrypted Worker secrets, then discoflare.com discards its own session. An operator can alternatively create one Account Admin Token and submit it directly on that Worker origin.

After Managed Setup installs Admin, Admin immediately creates the first base Installation on `workers.dev` with D1, R2, KV, core Durable Objects, Workers AI, Browser Run, and an Owner Setup Claim. Agent Computer, RealtimeKit, custom domains, and email remain explicit later actions from Workspace Settings. Discoflare Admin also discovers every marked Installation in the account and owns creation, updates, repair, and those optional infrastructure operations. The broad credential never enters an Installation. Each workspace instead receives a service binding to Admin and a per-Installation capability derived from Admin's stable session secret and accepted only by fixed operation allowlists. Workspace chat and data continue without Admin; infrastructure changes and new Huddle API calls require it.

Cloudflare grants still use account and zone resource boundaries. A dedicated Cloudflare account therefore provides the strongest isolation; an existing paid account shares its authority boundary across the Installations that Admin manages. The source/CLI deployment path remains an operator escape hatch. Admin stores either the renewable Managed Setup OAuth credential or an operator-supplied account token connected on the Admin origin.
