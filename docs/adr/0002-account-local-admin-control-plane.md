# Keep deployment authority in one account-local Discoflare Admin

Discoflare has one account-local control-plane binary with two setup modes. Each Cloudflare account contains one small Worker named `discoflare-admin`, protected by Cloudflare Access. Managed Setup uses a public PKCE OAuth client with refresh tokens and transfers that renewable grant into Admin before discoflare.com discards its copy. Private Setup uses temporary OAuth only to create or repair Admin; the operator then creates one Account Admin Token and submits it directly to that private Worker origin.

Discoflare Admin discovers every marked Installation in the account and owns creation, updates, repair, RealtimeKit provisioning, and eligible email infrastructure. The broad token never enters an Installation. Each workspace instead receives a service binding to Admin and a derived per-Installation capability accepted only by a fixed RealtimeKit operation allowlist. Workspace chat and data continue without Admin; infrastructure changes and new Huddle API calls require it.

Cloudflare grants still use account and zone resource boundaries. A dedicated Cloudflare account therefore provides the strongest isolation; an existing paid account shares its authority boundary across the Installations that Admin manages. The source/CLI deployment path remains an operator escape hatch. Managed and Private differ only in how the same Admin receives and renews its Cloudflare credential.
