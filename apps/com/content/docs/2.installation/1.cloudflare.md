The guided product has one control plane per Cloudflare account: a small Worker named `discoflare-admin`. [Managed Setup](/deploy) creates or repairs that Worker, stores its renewable OAuth credential as encrypted Worker secrets, and immediately creates the first base workspace. [Private Setup](/deploy/private) creates the same Worker with temporary OAuth and leaves Account Admin Token connection and workspace creation to the operator. Admin uses Cloudflare OAuth login and a stateless encrypted cookie; it needs neither Cloudflare Access nor D1.

## Before you begin

You need:

- a Cloudflare account;
- enough Cloudflare permissions to grant the Managed Setup scopes;
- R2 enabled, including Cloudflare's subscription checkout even when storage remains inside the free tier;
- Workers Paid only before enabling Agent Computer, because it uses Containers; and
- an active DNS zone only for a custom workspace hostname or workspace email.

A dedicated Cloudflare account provides the strongest isolation. The managed OAuth credential or Account Admin Token is account- and zone-scoped, so every Installation managed by one Admin shares that Cloudflare authority boundary. Using an existing paid account avoids another account-level Workers Paid subscription.

### One mail-enabled workspace per DNS zone

Cloudflare exposes one catch-all email rule per zone. Discoflare uses it so Mailboxes can be created inside the workspace without retaining a Cloudflare API token or adding a routing rule for every address. Separate application subdomains still share that catch-all: if `hq.example.com` has workspace mail, `dev1.example.com`, `dev2.example.com`, and `dev3.example.com` can use custom application domains but must leave workspace mail disabled. Use separate active Cloudflare zones when every installation needs independent mail. A shared zone mail-router is not part of the current release.

## 1. Install Discoflare Admin

Open [Managed Setup](/deploy), connect Cloudflare, and select the account. The installer creates or repairs:

- one `discoflare-admin` Worker on the account's `workers.dev` subdomain; and
- one renewable managed OAuth credential stored as encrypted Worker secrets; and
- the first `discoflare` workspace on `workers.dev` with D1, R2, KV, core Durable Objects, Workers AI, Browser Run, and a private Owner Setup Claim.

It does not create an Access application, RealtimeKit app, custom domain, email route, Agent Workflow, Container application, or Account Admin Token. The operator does not register an OAuth client: the Discoflare client and callback are reused for later Admin identity sign-ins. The OAuth session is removed from discoflare.com after bootstrap; the renewable credential remains only in Admin.

::docs-verification{title="Verify the bootstrap result"}
The page must report a Discoflare Admin version and return the Admin URL. A successful OAuth redirect or an existing Worker alone is not completed bootstrap evidence.
::

## 2. Create the Owner

After Admin verifies the base workspace, the browser opens its private Owner Setup Claim. Create the Owner name and password there; the workspace then signs the Owner in. The claim is carried in the URL fragment, removed from the address bar before submission, and becomes unusable after the Owner and Workspace are created.

Later Admin sign-ins use the same global OAuth client through discoflare.com to verify that the configured owner still belongs to the account. Admin then stores only an encrypted session cookie. For Private Setup, follow Admin's token-template link, create one Account Admin Token, and paste the one-time value into Admin. It travels directly from your browser to your own Admin Worker and never passes through discoflare.com. Workspace Workers receive neither the managed OAuth credential nor the account token, and expose no general Cloudflare API proxy.

::docs-verification{title="Verify the authority boundary"}
After connecting, Admin must list the marked Discoflare Installations in the selected account. Workspace Worker settings must contain the `DISCOFLARE_ADMIN` service binding and a secret `DISCOFLARE_ADMIN_CAPABILITY`, but no `DISCOFLARE_ADMIN_TOKEN`.
::

## 3. Add capabilities when needed

Open **Workspace Settings → Cloudflare** to:

- enable Agent Computer after the account has Workers Paid;
- enable RealtimeKit Huddles;
- select an active Cloudflare zone and connect a custom subdomain; and
- connect workspace email to the same subdomain on the Primary Installation.

The workspace sends only those fixed requests to Admin through its service binding and per-Installation capability. Admin stops instead of replacing a hostname, non-Cloudflare MX records, or a foreign catch-all rule.

Additional workspaces created in Admin also start with the same base profile. Existing resources and enabled capabilities are preserved during updates and repair.

## 4. Verify the workspace

Check the workspace health endpoint before and after setup:

```bash
curl -fsS https://chat.example.com/api/setup/health
```

After setup it should report `ok: true`, `ready: true`, and the deployed version. Then sign out and back in, send and reload a message, and round-trip an attachment. If Agent Computer or Huddles are enabled later, verify each after its separate deployment completes.

## Updates and repair

Discoflare Admin compares every discovered Installation with stable workspace GitHub Releases. Update and repair operate in place against the existing storage and runtime resources. Workspace **Settings → Updates** links back to Admin; a workspace cannot self-update with a broad token.

The separately versioned Admin release can be repaired by running the matching [managed](/deploy) or [private](/deploy/private) setup again. Existing account-token and session secrets are preserved; Managed Setup refreshes its stored OAuth credential when no account token is connected.

## Repository deployment

The **Deploy with GitHub** path remains for operators who want to own a fork and Workers Builds configuration. It is not a second guided product mode. You manually create and bind every resource, apply migrations, configure secrets and integrations, attach the hostname, and verify the runtime.

::docs-verification{title="A build is only one evidence layer"}
Record the resource IDs, migration result, Worker version, hostname, health response, Owner setup, browser realtime, attachment persistence, and Agent Task result separately.
::
