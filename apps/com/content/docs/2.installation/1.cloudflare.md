The guided product has one control plane per Cloudflare account: a small Worker named `discoflare-admin`. [Managed Setup](/deploy) creates or repairs that Worker, protects it with Cloudflare Access, and transfers a renewable OAuth grant into it. [Private Setup](/deploy/private) creates the same Worker with temporary OAuth and leaves Account Admin Token connection to the operator. Workspace creation happens afterward inside your own account.

## Before you begin

You need:

- a Cloudflare account;
- an email address allowed into Discoflare Admin;
- Workers Paid before creating workspace Installations, because Agent Computers use Containers; and
- an active DNS zone only for a custom workspace hostname or workspace email.

A dedicated Cloudflare account provides the strongest isolation. The Managed OAuth Grant or Account Admin Token is account- and zone-scoped, so every Installation managed by one Admin shares that Cloudflare authority boundary. Using an existing paid account avoids another account-level Workers Paid subscription.

### One mail-enabled workspace per DNS zone

Cloudflare exposes one catch-all email rule per zone. Discoflare uses it so Mailboxes can be created inside the workspace without retaining a Cloudflare API token or adding a routing rule for every address. Separate application subdomains still share that catch-all: if `hq.example.com` has workspace mail, `dev1.example.com`, `dev2.example.com`, and `dev3.example.com` can use custom application domains but must leave workspace mail disabled. Use separate active Cloudflare zones when every installation needs independent mail. A shared zone mail-router is not part of the current release.

## 1. Install Discoflare Admin

Open [Managed Setup](/deploy), connect Cloudflare, select the account, and enter the Admin email. The installer creates or repairs:

- one `discoflare-admin` Worker on the account's `workers.dev` subdomain; and
- one Cloudflare Access application allowing that email through one-time PIN.

It does not create a workspace, D1 database, R2 bucket, KV namespace, RealtimeKit app, or email route. The renewable OAuth grant is moved into Admin as encrypted Worker secrets and removed from the discoflare.com session after bootstrap.

::docs-verification{title="Verify the bootstrap result"}
The page must report a Discoflare Admin version and return the Admin URL. A successful OAuth redirect or an existing Worker alone is not completed bootstrap evidence.
::

## 2. Open the account-local control plane

Open the Admin URL through Cloudflare Access. Managed Setup is already connected and refreshes OAuth locally in Admin. Discoflare.com keeps only a non-secret Admin link in this browser profile; it cannot service workspace or Huddle runtime calls.

For Private Setup, follow Admin's token-template link, create one Account Admin Token, and paste the one-time value into Admin. It travels directly from your browser to your own Admin Worker and never passes through discoflare.com. Workspace Workers receive neither credential nor a general Cloudflare API proxy.

::docs-verification{title="Verify the authority boundary"}
After connecting, Admin must list the marked Discoflare Installations in the selected account. Workspace Worker settings must contain the `DISCOFLARE_ADMIN` service binding and a secret `DISCOFLARE_ADMIN_CAPABILITY`, but no `DISCOFLARE_ADMIN_TOKEN`.
::

## 3. Create or adopt an Installation

From Discoflare Admin:

1. choose **New installation**, or select **Adopt and update** for an existing marked Worker;
2. enter the Worker name, workspace name, and first Owner email;
3. choose invite-only or open registration;
4. optionally choose a custom hostname; and
5. keep the tab open while Admin provisions and verifies the release.

Huddles are enabled by default. The first eligible custom-domain Installation becomes Primary and also receives workspace Email Routing and Email Sending. Admin stops instead of replacing a hostname, non-Cloudflare MX records, or a foreign catch-all rule.

Admin creates the workspace Worker, D1, R2, KV, Durable Objects, Workflow, Workers AI binding, Agent Computer Container, migrations, public hostname, and private Owner Setup Claim. Existing resources are reused during adoption and updates.

## 4. Create and verify the Owner

Open the private setup URL returned by Admin. The claim is carried in the URL fragment, removed from the address bar before submission, and becomes unusable after the Owner and Workspace are created.

Check the workspace health endpoint before and after setup:

```bash
curl -fsS https://chat.example.com/api/setup/health
```

After setup it should report `ok: true`, `ready: true`, the deployed version, and configured Huddles. Then sign out and back in, send and reload a message, round-trip an attachment, and run an Agent Task after Container provisioning finishes.

## Updates and repair

Discoflare Admin compares every discovered Installation with stable workspace GitHub Releases. Update and repair operate in place against the existing storage and runtime resources. Workspace **Settings → Updates** links back to Admin; a workspace cannot self-update with a broad token.

The separately versioned Admin release can be repaired by running the matching [managed](/deploy) or [private](/deploy/private) setup again. Existing private token secrets are preserved; managed setup replaces its renewable OAuth grant.

## Repository deployment

The **Deploy with GitHub** path remains for operators who want to own a fork and Workers Builds configuration. It is not a second guided product mode. You manually create and bind every resource, apply migrations, configure secrets and integrations, attach the hostname, and verify the runtime.

::docs-verification{title="A build is only one evidence layer"}
Record the resource IDs, migration result, Worker version, hostname, health response, Owner setup, browser realtime, attachment persistence, and Agent Task result separately.
::
